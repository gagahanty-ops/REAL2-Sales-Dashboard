## Единственный технический блокер — право на push

Push отклонён: `Permission to sarrinoj-glitch/REAL2-Sales-Dashboard.git denied to gagahanty-ops` (HTTP 403). `gh api repos/sarrinoj-glitch/REAL2-Sales-Dashboard --jq '.permissions'` возвращает `{"admin":false,"maintain":false,"pull":true,"push":false}`. И HTTPS-токен, и SSH-ключ на машине принадлежат одному аккаунту `gagahanty-ops`: `ssh -T git@github.com` проходит, но `git push --dry-run` падает. Обойти нельзя — право выдаёт владелец репозитория.

Два варианта разблокировки:

1. Выдать аккаунту `gagahanty-ops` право записи (Collaborator: Write), после чего push идёт обычным образом.
2. Забрать коммиты бандлом со своего аккаунта:

```bash
git fetch ~/Desktop/REAL2-task2.bundle feat/foundation-access:task2
git merge --ff-only task2      # в клоне, находясь на feat/foundation-access
git push origin feat/foundation-access
```

После push сверить local, tracking и `git ls-remote`.

## Что делает владелец

Ни одно из этих действий не выполняется кодом, миграцией, тестом или агентом. Полный порядок — `docs/runbooks/production-go-live.md`.

1. **Разблокировать push** — право записи или приём бандла (см. выше).
2. **Установить внешнюю OAuth-интеграцию amoCRM.** Приватная интеграция запрещена. До установки нужно письменное подтверждение поддержки amoCRM, что внешняя интеграция не отменяет техподдержку. Redirect URI ровно один: `https://<домен>/api/integrations/amo/callback`, посимвольно совпадающий с `AMO_REDIRECT_URI`. Права только на чтение. Порядок — `docs/runbooks/amo-oauth-installation.md`.
3. **Решение 1: включить синхронизацию.** `SYNC_ENABLED=true` в файле секретов воркера **и** `update system_controls set enabled = true, reason = '<кто, дата>' where key = 'sync_enabled';`. Затем час наблюдать `/system` и `/sync`. Откат — обратная операция, данные не теряются.
4. **Теневая сверка 7–14 полных календарных дней.** Система считает те же показатели, что ручной отчёт, но ничего не публикует. Каждый день: выгрузка CSV с колонками `Дата; Менеджер; Лиды; Заявки; Оплаты; Выручка`, сверка на `/reconciliation?from=<дата>&to=<дата>`, разбор расхождений до конкретных `amo_lead_id`. День принимается только при нулевом расхождении. Ожидаемое значение переписывать запрещено. Результат каждого дня — файл `docs/runbooks/release-evidence/<дата>-reconciliation.md` с именем выгрузки, её SHA-256, версией снимка, числом строк и решением. Порядок — `docs/runbooks/shadow-acceptance.md`.
5. **Вручную создать копию Google-таблицы** и выдать сервисному аккаунту доступ Editor **только на копию**. Оригинал `123QVhKGG3Y6ZlyHYnuKG_1BPhS82FcYaqY96nsB7Iks` не расшаривается никогда. Затем на `/settings/google-sheet`: зарегистрировать цель, задать диапазоны, пройти проверку раскладки, активировать.
6. **Решение 2: включить публикацию.** Только после пройденной теневой сверки, репетиции восстановления (`bash scripts/verify-backup-restore.sh --fixture packages/testkit/fixtures/backup.sql`), прогона гейтов на боевом образе и письменной приёмки отчёта. `SHEET_PUBLISH_ENABLED=true` **и** `update system_controls set enabled = true, ... where key = 'sheet_publish_enabled';`. Первая публикация — в присутствии владельца, сразу со сверкой контрольной суммы и содержимого копии.

Каталог `docs/runbooks/release-evidence/` сейчас содержит только `.gitkeep`: ни одного дня сверки, ни вывода репетиции восстановления, ни подписи владельца там ещё нет. Доказательства релиза не накоплены вовсе — вердикт GO выдавать не на чем.

## Безопасность на конец сессии

- Оба внешних переключателя выключены: `SYNC_ENABLED=false` и `SHEET_PUBLISH_ENABLED=false` в `.env.example`, в `docker-compose.yml` они заданы литеральной строкой `"false"`, `deploy/docker-compose.production.yml` их намеренно не выставляет вовсе. В БД контроли `sync_enabled` и `sheet_publish_enabled` стартуют выключенными.
- В коде есть только `disableSystemControl` (`packages/db/src/identity.ts`) — функции включения переключателя нет намеренно. Код имеет право сам выключить публикацию при расхождении контрольной суммы или дрейфе раскладки, но никогда не включает.

- Реального `.env` в репозитории нет; `.env.e2e` содержит только локальные значения и игнорируется `.gitignore:19`.

## Открытые расхождения документации

Работа над кодом закрыта, но три расхождения между нормативными документами и фактом остались не оформленными:

1. **UI-стек.** `SPEC.md` §0.2 и план 4 объявляют Tailwind CSS 4, shadcn/ui, Recharts 3 и TanStack Query 5. Ни один из них не установлен: `apps/web` использует рукописный `globals.css`, серверные компоненты и инлайновый SVG-график. Отклонение зафиксировано решением RD1 только во внутреннем журнале `.superpowers/sdd/2026-09-12-04-dashboard-ui/progress.md`. В SPEC не исправлено, ADR в `docs/decisions/` не заведён, записи в `docs/spec-first/APPROVALS.md` нет. По правилу `CLAUDE.md` расхождение кода и документации должно закрываться правкой спецификации через ревью.
2. **Имена миграций в планах иллюстративны.** Фактический ряд — `0001`…`0012` подряд. План 2 называет `0003`/`0004` (реально `0004`/`0005`), план 3 — `0006_metric_snapshots` (реально `0011`), план 5 — `0007_sheet_publication_and_alerts` (реально `0012`). Объяснены только случаи планов 2 и 5; случай плана 3 нигде не задокументирован.
3. **`specs/features/`.** `SPEC.md` §13 требует отдельный файл спецификации на каждую из 12 фич. Каталога `specs/` в репозитории нет — его роль фактически взяли планы и `docs/spec-first/SPEC_COVERAGE.md`. В SPEC это не переписано.

Дополнительно в планах 2 и 5 в строке Tech Stack осталось «PostgreSQL 16», хотя ADR `docs/decisions/0001-postgresql-17.md`, SPEC §0.2 и `supabase/config.toml` фиксируют PostgreSQL 17.
