# Как новому агенту немедленно продолжить REAL2 Sales Dashboard

Это основной cold-start handoff. Сначала восстановить контекст и проверить контрольную точку, только потом менять код. Plan 3 Task 2 (deterministic normalization) реализована и одобрена ревью, но **DB-часть полного gate ещё не выполнена** (на машине `ishop` нет Docker/Supabase). Первое действие — прогнать полный gate на машине с локальным Supabase; только потом начинать **Plan 3 Task 3**.

## 1. Проект и бизнес-смысл

REAL2 Sales Dashboard — безопасный отдельный dashboard и серверный контур отдела продаж «РЕАЛ ДВА». Он читает amoCRM через внешнюю OAuth-интеграцию, нормализует сделки, считает утверждённые метрики и позднее публикует результат в отдельную Google-таблицу/дашборд.

- «Создана заявка» — вход лида в «Завершение (самовывоз или доставка)».
- «Клиент произвёл оплату / реализация» — «Успешно реализовано».
- Когорты считаются по дате создания заявки.
- Точные формулы и спорные случаи определяет `METRICS_CATALOG.md`, не догадки разработчика.
- Метод: Spec First → failing test → минимальный код → независимое ревью → полный verification gate.

## 4. Неприкосновенные ограничения

Без нового явного разрешения владельца запрещено:

- использовать приватную интеграцию amoCRM;
- изменять business-данные amoCRM;
- отправлять `PATCH`, `PUT`, `DELETE` или business `POST` в amoCRM;
- устанавливать production OAuth, выполнять live sync или обращаться к live Google API;
- включать `SYNC_ENABLED` или `SHEET_PUBLISH_ENABLED`;
- редактировать Google Sheet `123QVhKGG3Y6ZlyHYnuKG_1BPhS82FcYaqY96nsB7Iks`;
- сохранять токены, `.env`, OAuth code, client secret, private/service-role key или реальные payloads в чат, vault или git;
- переписывать чужие незакоммиченные изменения или изменять старые применённые миграции без review-решения.

Архитектура amoCRM: только **внешняя OAuth-интеграция** и read-only business API. Единственный допустимый `POST` транспорта — `/oauth2/access_token`.

## 6. Проверка стартовой точки

Использовать Node 22:

- машина `arlandorizzi`: `/opt/homebrew/opt/node@22/bin` (системная Node 25 там не грузит `simdjson.31`);
- машина `ishop`: `~/.local/node22/bin` (официальный tarball).

В свежем клоне перед `pnpm typecheck` нужен `pnpm build`: `@real2/integrations` отдаёт типы из `dist/`.

```bash
cd /Users/arlandorizzi/Desktop/REAL2-Sales-Dashboard
export PATH=/opt/homebrew/opt/node@22/bin:$PATH
node --version
pnpm --version
git status --short --branch
git rev-parse HEAD

```

Ожидается: Node 22, ветка `feat/foundation-access`, чистое дерево и три одинаковых hash (последний docs-коммит Task 2). При чужих изменениях ничего не стирать.

Проверить только switches, не выводя остальные секреты:


Оба должны оставаться `false`.

## 7. Точная следующая задача

1. Закрыть DB-часть gate Task 2. На машине с Docker и Supabase CLI выполнить раздел 9 на HEAD. Ожидаемо:
   - integration 86/86;
   - security 24/24;
   - repo/worker 16/16;
   - unit 333/333.

   Результат записать в `progress.md` (ledger Task 2) и в память.
2. Если что-то упало — сначала systematic debugging. Task 2 не меняла SQL, репозитории и интеграции, поэтому ищите причину в окружении или в фикстурах.
3. После зелёного gate начать **Plan 3 Task 3** — `buildLeadHistory` / `normalizeSyncRun`:
   - учесть handoff notes из `progress.md`: ISO-строки → `Date`, судьба ранее сохранённых строк для `excluded`/`rejected`, `sourceFieldId: null` при ненайденном поле, `pipelineStatusIds` из той же sync run;
   - Task 4 должна покрыть все коды Task 2.

## 8. Порядок выполнения задачи

1. Полностью перечитать задачу и связанные требования SPEC/METRICS_CATALOG.
2. Создать `.superpowers/sdd/2026-09-12-03-normalization-metrics/task-N-brief.md`.
3. В `progress.md` записать фактическую стартовую точку.
4. Сначала failing tests, сохранить red evidence.
5. Минимальная реализация, green, refactor, повторный green.
6. Маленький самостоятельный implementation commit.
7. Независимое review, fix rounds, повторное review.
8. Полный controller verification gate.
9. Только после свежих результатов отметить plan checkboxes и обновить ledger/report/память, затем push и сверка remote.

## 9. Полный verification gate

```bash
export PATH=/opt/homebrew/opt/node@22/bin:$PATH
supabase db reset
pnpm test:integration
pnpm test:security
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm check:secrets
git diff --check
```

Последний полный DB-baseline (Task 1, машина arlandorizzi): integration 86/86, security 24/24, repo/worker 16/16, unit 110/110.

Task 2 на машине `ishop` без БД:

- прошли lint, typecheck, build, contracts, secret scan и diff check;
- repo/worker 16/16;
- unit 317/333 — все 16 падений в DB-зависимом `oauth.test.ts`;
- integration 12/86 и security 5/24 — остальное требует БД.

Не объявлять успех по старым результатам или только по отчёту другого агента.

## 10. Как сохранять память

После каждой задачи обновить рабочий SDD и его отслеживаемую копию:

```text
.superpowers/sdd/2026-09-12-03-normalization-metrics/progress.md
.superpowers/sdd/2026-09-12-03-normalization-metrics/task-2-report.md
.superpowers/sdd/2026-09-12-03-normalization-metrics/task-N-review.md
```

`.superpowers/sdd` игнорируется source git (на машине `ishop` — через `.git/info/exclude`), поэтому скопировать её в `project-memory/raw-context/sdd/2026-09-12-03-normalization-metrics/`. Также обновить текущий статус, этот handoff, `project-memory/MANIFEST.md` и новую запись в `project-memory/sessions/`. Bundle больше не нужен: память и код живут в одном репозитории. Не сохранять секреты.

## 11. Как закончить будущую сессию

1. Остановиться на целостной границе и честно записать незавершённое.
2. Проверить единый worktree.
3. Скопировать SDD evidence в `project-memory/` и обновить handoff.
4. Проверить секреты и полный verification gate.
5. Одним коммитом закоммитить код и память, push source и сверить local, tracking, `git ls-remote`.
6. В отчёте назвать один hash и следующую незапущенную задачу.
