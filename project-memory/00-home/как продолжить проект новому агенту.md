# Как продолжить проект новому агенту

Это точка входа. Инструкция, а не описание: выполняй сверху вниз.

## 1. Что это за проект

REAL2 Sales Dashboard — отдельный дашборд отдела продаж «РЕАЛ ДВА», который читает amoCRM в режиме read-only, нормализует сделки, считает утверждённые метрики и неизменяемые снимки, а потом (опционально) публикует их в **копию** Google-таблицы. Всё внешнее закрыто двумя выключателями сразу (переменная окружения И запись в БД `system_controls`), оба выключены, и код умеет их только выключать — включает только владелец руками. Код по всем пяти планам написан и загейчен; проект стоит не на технике, а на действиях владельца: доступ на push, установка OAuth amoCRM, теневая сверка 7–14 дней, создание копии таблицы.

## 3. Окружение и проверки — копипастой

Рабочая копия: `/Users/ishop/Desktop/REAL2-Sales-Dashboard.nosync` (`~/Desktop/REAL2-Sales-Dashboard` — симлинк на неё). Суффикс `.nosync` обязателен: рабочий стол синхронизируется с iCloud, и при почти полном диске macOS выгружает файлы и `node_modules` в облако (`dataless`), после чего eslint, тесты и git падают случайным образом.

### Node 22 — без этого не стартует вообще ничего

`engines.node = "22.x"` плюс `engine-strict=true` в `.npmrc`. Системная Node — v26.9.0, на ней любая команда pnpm падает с `ERR_PNPM_UNSUPPORTED_ENGINE`. Состояние шелла между вызовами не сохраняется, поэтому PATH ставь **в каждой команде**:

```bash
export PATH=/opt/homebrew/opt/node@22/bin:$PATH   # v22.23.2, keg-only, не слинкована
# запасной вариант, поставлен tarball-ом:
# export PATH=$HOME/.local/node22/bin:$PATH
```

Менеджеров версий (nvm, asdf, fnm, mise, volta) на машине нет.

### Локальная БД

Docker Desktop не ставился. Используется colima + lima + docker CLI + Supabase CLI, всё вручную в `~/.local`:

```bash
export PATH=$HOME/.local/bin:$HOME/.local/lima/bin:$HOME/.local/node22/bin:$PATH
colima status || colima start --vm-type vz --cpu 2 --memory 3 --disk 12
cd /Users/ishop/Desktop/REAL2-Sales-Dashboard.nosync
```

Требование `docs/runbooks/local-development.md` — **не менее 10 ГБ свободного места**. Сейчас на томе ~7.7 ГБ из 228 ГБ (97 % занято): перед пересозданием VM или сборкой образов чисти только восстановимые кэши, пользовательские данные (CrossOver 50 ГБ, Claude 11 ГБ, Steam) не трогай.

## 4. Рабочий метод

1. **Spec-first.** Сначала читаешь SPEC и METRICS_CATALOG, потом план, потом код. Меняешь бизнес-смысл — сначала правишь спецификацию через ревью и записываешь решение, молча не меняешь никогда.
2. **Бриф до кода.** Пиши `.superpowers/sdd/<план>/task-N-brief.md` с нумерованными решениями (R1, R2, …). Каталог `.superpowers/sdd/` исключён из git через `.git/info/exclude`, поэтому обязательно зеркаль его в `project-memory/raw-context/sdd/<план>/` — иначе материалы задачи не попадут в коммит.
3. **TDD.** Сначала падающий тест, сохраняешь red-вывод; потом минимальная реализация до green; потом рефакторинг и повторный green.
4. **Мутационная проверка — обязательна.** После зелёного вноси по одному намеренному дефекту в продакшн-код и убеждайся, что тест краснеет, затем восстанавливай файл. Делается python3-скриптом: словарь `{ключ: путь}`, список `(метка, файл, старая строка, новая строка)`, перед каждой заменой `assert s.count(old) == 1`. Выжившая мутация — это дыра в тестах или лишний дублирующий код, а не повод ослабить проверку.
5. **Один коммит — одно изменение.** Реализация отдельно, fix-раунды ревью отдельно, docs/checkpoint отдельно. Трейлер: `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.
6. **Полный гейт перед коммитом** (раздел 3). Не объявлять успех по старым результатам, по отчёту другого агента или по частичному прогону.
7. **Задачи строго последовательно.** Следующая не начинается, пока предыдущая не реализована, не загейчена, не отревьюена независимо и не зафиксирована в плане, SDD и памяти.
8. **Диагностика без догадок.** Симптом объясняется до конца, прежде чем чинить. В этом проекте уже дважды ошибочный диагноз («нехватка соединений», «помеха окружения») стоил лишних правок: настоящей причиной были оставленные фикстуры в общей БД.
9. **Автономность.** Мелкие развилки решай сам, спрашивай только про необратимое (включение флагов, боевые доступы, удаление чужих данных).

## 5. Чего нельзя никогда

Подробности — в [[проект нельзя ломать в amoCRM и нельзя трогать исходную Google таблицу]], [[интеграция amoCRM только внешняя OAuth и только read-only]] и [[исходная Google таблица навсегда защищена от записи]]. Коротко:

- Приватная интеграция amoCRM. Только внешняя OAuth.
- Любой `PATCH`, `PUT`, `DELETE` или business-`POST` в amoCRM. Единственный разрешённый POST — `/oauth2/access_token`, остальное — GET по белому списку через `amoFetch`.
- Запись в оригинальную Google-таблицу `123QVhKGG3Y6ZlyHYnuKG_1BPhS82FcYaqY96nsB7Iks` (denylist в коде + check-constraint в БД).
- Включать `SYNC_ENABLED` или `SHEET_PUBLISH_ENABLED` в любом виде — ни в коде, ни в миграции, ни в деплой-файле, ни в БД. Функции включения контроля в коде нет намеренно, есть только `disableSystemControl`.
- Выводить в чат, логи, коммиты или память содержимое `.env*`, токены, ключи, OAuth code, полные телефоны и raw payload amoCRM.
- Удалять нормализованные строки проблемных сделок (вместо удаления — эскалация проблемы качества) и принимать коды `missing_stage_history` и `E_SHEET_PROTECTED` как исключения.
- Подгонять ожидаемые тоталы тестов под фактический вывод. Изменение определения метрики — только через METRICS_CATALOG.
- Менять уже применённые миграции `0001..0012` и переписывать чужие незакоммиченные изменения.
- Рапортовать о непроверенном. Владелец однажды предложил «сказать, что докер скачан» — правильный ответ был отказаться и реально поставить.
