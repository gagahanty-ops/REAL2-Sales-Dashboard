# Контур безопасности: где каждый запрет закреплён в коде

Запреты проекта держатся не на дисциплине агента, а на механизмах: замороженная константа, ограничение целостности, триггер базы, тест. Эта заметка перечисляет каждый запрет и точное место, где он живёт. Проверено чтением кода 20 сентября 2026 на HEAD `9127774`.

## 1. Исходная Google-таблица не получает записи никогда

Защищённый идентификатор: `123QVhKGG3Y6ZlyHYnuKG_1BPhS82FcYaqY96nsB7Iks`.

**Механизм первый — замороженная константа в коде.**
`packages/integrations/src/google/policy.ts`:

```ts
export const PROTECTED_SPREADSHEET_IDS: ReadonlySet<string> = Object.freeze(
  new Set(["123QVhKGG3Y6ZlyHYnuKG_1BPhS82FcYaqY96nsB7Iks"]),
);
```

Набор нельзя расширить или опустошить ни переменной окружения, ни строкой в базе, ни запросом, ни через интерфейс.

**Механизм второй — проверка до получения секретов.**
`assertWritableSpreadsheetId(spreadsheetId, expectedTargetId)` вызывается первой строкой и в `createSheetReadClient`, и в `createSheetWriteClient` — до `readGoogleServiceAccount()` и до создания клиента. Порядок принципиален: при защищённом идентификаторе учётные данные даже не читаются, клиента не существует, сетевой запрос невозможен в принципе.

Функция отказывает в четырёх случаях:

| Условие | Ошибка |
| --- | --- |
| идентификатор не проходит `/^[A-Za-z0-9_-]{20,200}$/` | `E_VALIDATION` 422 |
| идентификатор в защищённом наборе | `E_SHEET_PROTECTED` 403 |
| ожидаемая цель сама защищена | `E_FORBIDDEN` 403 |
| идентификатор не совпадает с активированной целью | `E_FORBIDDEN` 403 |

Последняя строка важна отдельно: писать можно только в ту единственную копию, которую администратор зарегистрировал и активировал. Любой другой корректный идентификатор отвергается.

**Механизм третий — ограничение целостности в базе.**
`supabase/migrations/0012_sheet_publication_and_alerts.sql:25`:

```sql
check (spreadsheet_id <> '123QVhKGG3Y6ZlyHYnuKG_1BPhS82FcYaqY96nsB7Iks'),
```

Защищённый идентификатор нельзя даже сохранить как цель публикации. Ошибка кода не спасёт, потому что строка не запишется.

Подробнее про границу — [[исходная Google таблица навсегда защищена от записи]].

## 2. Публикация требует двух независимых разрешений

`createSheetWriteClient` в `packages/integrations/src/google/policy.ts` проверяет по порядку:

1. `context.publishEnabledInEnvironment` — переключатель окружения (`SHEET_PUBLISH_ENABLED`);
2. `await context.controls.isPublishEnabled()` — управляющая запись в базе (`sheet_publish_enabled`).

Порядок выбран намеренно: выключенное развёртывание даже не обращается к базе за вторым флагом.

Клиент на чтение (`createSheetReadClient`) переключателей не проверяет — проверка раскладки копии безопасна и нужна до включения публикации.

Оба переключателя стартуют выключенными, `supabase/migrations/0001_identity_and_controls.sql:31-32`:

```sql
('sync_enabled', false, 'disabled until staging safety gate'),
('sheet_publish_enabled', false, 'disabled until shadow acceptance');
```

**Код умеет только выключать.** В `packages/db/src/identity.ts` есть `disableSystemControl` (строка 118), который выставляет `enabled = false`. Парной функции включения не существует — во всём пакете нет ни одного `set enabled = true`. Включает человек, вручную, двумя независимыми действиями: правка файла секретов и `update system_controls`.

Практическое следствие: агент физически не может включить синхронизацию или публикацию, даже если его об этом попросят. Максимум — выключить.

## 3. Бизнес-данные amoCRM не изменяются

`packages/integrations/src/amo/policy.ts`, функция `assertAmoRequestAllowed`.

**Хост прибит намертво:**

```ts
const AMO_HOST = "555151.amocrm.ru";
```

Отвергается всё, что не `https:`, не этот хост, а также любой адрес с портом, именем пользователя или паролем в URL. Это закрывает подстановку чужого адреса через данные запроса.

**Методы.** Единственный разрешённый `POST` — ровно `/oauth2/access_token`. Всё остальное, кроме `GET`, даёт `E_AMO_METHOD_DENIED` 403. `PATCH`, `PUT`, `DELETE` не имеют пути в коде вообще.

**Пути.** Разрешённые адреса чтения перечислены списком регулярных выражений: учётная запись, пользователи, сделки (список и одна), пользовательские поля сделок, воронки со статусами, события. Путь вне списка — `E_AMO_PATH_DENIED` 403.

**Транспорт.** `packages/integrations/src/amo/transport.ts`, `amoFetch`:

- заголовок `authorization` из входящих заголовков **удаляется** и выставляется заново только для бизнес-запроса и только из провайдера токенов — клиентский токен подсунуть нельзя;
- `redirect: "error"` и отдельная проверка, что вызывающий не попросил другое поведение переадресации: перенаправление на чужой хост невозможно;
- отказ на этапе проверки тоже пишется в журнал с результатом `denied` — попытка видна.

## 4. Журналы не содержат ничего лишнего

Санитайзер работает по белому списку, а не по чёрному. `apps/web/src/lib/logging/logger.ts`, проверяется в `tests/security/log-redaction.security.test.ts`.

Из записи с телефоном, именем клиента, токеном, текстом SQL-запроса и телом с паролем остаётся ровно `level`, `message`, `trace_id`, `status`. Всё остальное отбрасывается по умолчанию — новое поле не утечёт само собой, потому что его нет в списке разрешённых.

Журнал обращений к amoCRM содержит только метод, нормализованный путь, длительность, идентификатор трассировки, номер попытки и результат. Значения фильтров, тела ответов и параметры запроса в него не попадают.

Оповещения подчиняются тому же правилу: в письме нет полезных нагрузок, токенов и строк подключения — только код, важность, счётчик и ссылка на runbook.

## 5. История не переписывается

Неизменяемость держат триггеры базы, а не соглашение.

| Что защищено | Где |
| --- | --- |
| версии конфигурации воронки, правила каналов, результаты валидации | `0004_amo_configuration.sql:94-117` |
| ячейки снимка, факты по сделкам, строки этапов | `0011_metric_snapshots.sql:113-125` |
| доказательства снимка | `0011_metric_snapshots.sql:149` |
| история планов продаж | `0011_metric_snapshots.sql:180-198` |
| завершённые попытки публикации и их доказательства | `0012_sheet_publication_and_alerts.sql:108-125` |

Триггеры срабатывают на попытку изменения и роняют операцию с `errcode = 'P0001'`.

Это поймали на практике: попытка вставить закрытую версию плана продаж напрямую в базу упала на `prevent_sales_plan_rewrite`. Правильный путь — через форму приложения, которая закрывает старую версию и создаёт новую. Подробности — [[грабли сессии 19 сентября и их истинные причины]].

Сырые страницы синхронизации живут по тому же правилу — [[сырые amoCRM страницы append only и курсор двигается только после полного success]].

## 6. Разграничение доступа

`tests/security/rls.security.test.ts` — 864 строки отрицательных проверок: менеджер не видит чужие сделки ни через интерфейс, ни через API, ни в экспорте. Проверки построены на существующих строках и доказывают, что запрещённое чтение возвращает пустоту, а не ошибку — иначе по коду ответа можно было бы угадать существование записи.

Отдельные роли базы: `service_worker`, `retention_worker`, `sheet_publisher` — каждая с минимально необходимыми правами.

## Правило для агента

Любое изменение, которое ослабляет хоть один пункт этой заметки, недопустимо — даже если о нём просят прямо и даже если оно выглядит временным. Ослабление защиты — это не «правка кода», а снятие гарантии, на которой держится доверие владельца к системе.

Если задача кажется невыполнимой без ослабления — задача сформулирована неверно, и об этом надо сказать, а не обойти защиту.
