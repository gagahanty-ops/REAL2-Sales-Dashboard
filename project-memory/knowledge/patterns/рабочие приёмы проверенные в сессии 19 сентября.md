## 1. TDD с проверкой мутацией

Зелёные тесты сами по себе ничего не доказывают: они могут проходить и на сломанном коде. Поэтому цикл в этом проекте состоит из пяти шагов, а не из трёх:

1. **Красный** — тест написан до реализации и падает («модуль не найден» или конкретное несовпадение).
2. **Зелёный** — минимальная реализация, тест проходит.
3. **Мутация** — в рабочий код вносится один заведомый дефект.
4. **Проверка** — набор обязан покраснеть именно на этом дефекте.
5. **Возврат** — исходник восстанавливается побайтово, набор снова зелёный.

Выжившая мутация — это не повод ослабить требование. Это либо дыра в тестах (дописать точный тест), либо лишний код (убрать дублирующую проверку).

### Как запускался прогон

Ранняя форма — shell-функция с бэкапом файла и `perl -0pi`. Рабочая форма, которой закрыты все задачи планов 3–5, — python3-heredoc:

```
python3 <<'PY'
files = {"norm": "packages/domain/src/leads/normalize-lead.ts"}
orig  = {k: open(v, encoding="utf-8").read() for k, v in files.items()}
muts = [
    ("channel fallthrough", "norm", "<точная старая строка>", "<сломанная строка>"),
    # ...
]
for label, key, old, new in muts:
    s = orig[key]
    assert s.count(old) == 1, (label, s.count(old))   # обязательно
    open(files[key], "w", encoding="utf-8").write(s.replace(old, new))
    # запустить нужный набор vitest, вынуть строку "Tests ..." из вывода
    open(files[key], "w", encoding="utf-8").write(orig[key])  # вернуть
PY
```

Два обязательных условия:

- `assert s.count(old) == 1` перед каждой заменой. Без него неточный якорь совпал не в той функции, правка размножилась и `esbuild` упал с `ERROR: Expected ";" but found "const"` — тест-файл перестал грузиться целиком (143 теста вместо ~230), лечилось `git checkout` файла.
- Замены с кириллицей делать **только** через python3 с `encoding='utf-8'`. `perl -pi` и даже `perl -CSD -pi` молча не заменяли строку, и тест продолжал падать по непонятной причине.

### Что реально поймали

Пойманные мутации (набор отработал как задумано):

- `packages/domain/src/leads/normalize-lead.ts` — 8 мутаций (проваливание правил канала, отключение сортировки правил, игнор `is_active`, отключение календарной логики, UTC вместо Москвы); после отката 215/215. Второй раунд после правок ревью — ещё 3 (снять маскирование, убрать раннее исключение вне воронки, убрать sentinel нетекстового источника), после отката 242/242, прогнано три раза подряд.
- `packages/domain/src/leads/build-history.ts` — 7 мутаций (нет tie-breaker по `amoEventId`, передача ответственности в тот же момент игнорируется, берётся последняя веха вместо первой, malformed payload проглатывается, дубликаты не схлопываются); после отката 33/33.
- `packages/db/src/normalize-run.ts` + `apps/worker/src/jobs/normalize-sync-run.ts` — 8 мутаций (устаревший ответственный сохранён, лид вне воронки сохранён как нормальный, won не отмечен, принят незавершённый прогон, проблемы качества потеряны); после отката 9/9.
- `packages/domain/src/metrics/aggregate.ts` — 7 мутаций (оплата без текущего won, выручка по всем лидам, дубли считаются дважды, процент округлён до целого, месяц сравнивается фиксированной длиной, группа `unassigned` первой).

Выжившие мутации и что с ними сделали — это самая ценная часть:

- **`blocking list unsorted`** в `evaluateQualityGate` — выжила, потому что `blockingCodes.sort()` дублировал уже отсортированный порядок каталога. Сортировку из гейта убрали, добавили тест «unsorted catalogue», который ловит нарушение порядка в самом `packages/domain/src/quality/codes.ts`.
- **`already accepted issue re-accepted`** и **`short reason allowed`** — выжили, потому что проверка статуса и длины причины дублировались между маршрутом и репозиторием. Дубль из `packages/db/src/quality.ts` убрали, оставили в zod-схеме маршрута и дописали прямые тесты репозитория.
- **`cross-foot check dropped`** в `apps/worker/src/jobs/build-snapshot.ts` — выжила, потому что каждый падающий кейс ломал сразу несколько инвариантов. Дописали два точечных теста: расхождение только в разбивках и итог вовсе без разбивки.
- **`candidate snapshot served`** — выжила, не было теста на указатель `current_snapshot`, ведущий к неутверждённому снимку. Дописали «refuses a pointer that leads to a snapshot which was never approved».
- **`stage age back on wall clock`** — выжила и вскрыла **настоящий дефект продукта**: `buildMetricSnapshot` считал возраст открытого этапа от `Date.now()`, из-за чего контрольная сумма снимка менялась между идентичными пересборками и контракт идемпотентности падал с `E_CONFLICT`. Параметр `now()` убрали из `BuildSnapshotDeps`, возраст меряется от `sourceFreshAt` — момента, когда данные прогона были истинны.

Готового мутационного раннера (stryker и т. п.) в проекте нет и не заводили: нужны осмысленные подмены инвариантов конкретного модуля, а не механические операторные мутации.

**Отдельное правило:** ожидаемые значения никогда не подгоняются под фактический вывод. Если тест не сходится с каталогом метрик — сначала разбирается причина, изменение определения метрики проходит через `raw-context/project-docs/METRICS_CATALOG.md`. Единственный случай правки золотых данных в этой сессии — цена `1000.55` → `1001.00`, и то потому, что amoCRM физически отдаёт цену целым числом рублей, то есть копеечная цена недостижима через живой конвейер. Копейки продолжают проверяться там, где реально возникают — в делении и среднем чеке. См. [[метрики считаются по дате создания лида в Москве]].

## 2. Скриншоты как обязательный шаг приёмки

Зелёный гейт не видит нечитаемую вёрстку: поведение правильное, а смотреть на экран невозможно. Владелец потребовал «покажи фронт» — и одна съёмка вскрыла шесть дефектов, которых не поймали 574 юнит-теста и 23 браузерных сценария.

### Как снимать

```
supabase start
pnpm build
lsof -ti tcp:3100 | xargs -r kill -9
set -a; source ./.env.e2e; set +a
pnpm tsx tests/e2e/seed.ts                      # печатает "seeded snapshot N"
nohup pnpm --filter @real2/web exec next start --port 3100 --hostname 127.0.0.1 > <лог> 2>&1 &
# дождаться: curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3100/api/health/live == 200
node <scratchpad>/shoot.mjs                     # 18 экранов, ожидается 18 строк "snapped"
```

Параметры контекста в `shoot.mjs`: viewport 1440×1100, `locale: ru-RU`, `timezoneId: Europe/Moscow`, `fullPage: true`. Логин формой: `input[name="email"]` = `e2e.admin@example.test`, пароль из `E2E_PASSWORD` (значение не переписывается никуда). Страница `/login` снимается отдельным анонимным контекстом. Диапазон дат во всех URL — `from=2026-09-05&to=2026-09-06`.

PNG показываются владельцу **прямо в переписке через Read на файл**, не вкладкой и не ссылкой. Цикл «правка → `pnpm build` → перезапуск 3100 → `node shoot.mjs` → Read png» повторяется, пока экран не станет читаемым.

### Что нашли скриншоты и не нашли тесты

- Подписи фильтров и строка «Итого» невидимы: дашбордные стили писались под светлый фон, а приложение тёмное (`apps/web/src/app/globals.css`: `color-scheme: dark`, `--page #071824`, `--panel #102b3b`, `--text #f5f8fa`). Лечение — выкинуть собственную палитру и писать только через токены.
- Дневной график — две гигантские плиты: `preserveAspectRatio="none"` растягивал SVG.
- В навигации по два пункта «Воронка» и «Каналы» — разделы дашборда и настроек назывались одинаково; настройки переименованы в «Настройка воронки» и «Правила каналов».
- `/leads/1001` отдаёт голый системный 404: сид не заполнял нормализованный слой и у маршрута не было своей `not-found.tsx`.
- На `/quality` и `/attention` печатались сырые коды (`unknown_channel`, `site`).
- Drill-down тащил чужой заголовок «Требует внимания», потому что переиспользовал панель целиком.
- Экраны алертов, снимка, истории публикаций и планов — голый текст на тёмном фоне, кнопка «Я увидел» уезжала за правый край, выпадающий список менеджеров в планах был пуст (строился из тех, у кого случайно есть лиды в окне отчёта, вместо реестра доступов).

Последний дефект чинился **структурно**: ритм секций вынесен в общий класс `.content` (`apps/web/src/app/globals.css:302`), чтобы новая секция физически не могла приехать приклеенной к заголовку. Точечная правка одного экрана повторила бы ту же ошибку на следующем.

Вывод для нового агента: перед словом «готово» — сверка со SPEC и просмотр экранов глазами. Отчёт о зелёных тестах готовностью не является.

## 3. Порядконезависимость тестов через полную очистку зависимых таблиц

Симптом: 16 юнит-тестов `packages/integrations/src/amo/oauth.test.ts` падают после прогона E2E с `duplicate key value violates unique constraint app_users_pkey` и `violates foreign key constraint pipeline_configs_amo_connection_id_fkey`.

**Ложный диагноз, который ставился дважды:** «живой E2E-сервер держит соединения с локальной БД, тестам их не хватает». Он даже был записан в `raw-context/sdd/2026-09-12-04-dashboard-ui/progress.md` как «Known interference» и дважды закрывал вопрос без починки.

Настоящая причина: браузерный гейт оставлял свои фикстуры в **общей** локальной БД (`fileParallelism: false`, одна база на все наборы), а `beforeEach` теста чистил только `public.oauth_states` и `public.amo_connections` — оставшаяся конфигурация воронки держала внешний ключ на удаляемое соединение.

Лечение в два уровня:

1. **Симптом** — `tests/e2e/cleanup.teardown.ts`, отдельный teardown-проект Playwright (`playwright.config.ts`: проект `dashboard` объявляет `teardown: "cleanup"`). Делает `truncate` ~30 таблиц `public.*` плюс `delete` из `oauth_states`, `amo_connections`, `app_users`; при пустом `DATABASE_URL` тихо выходит, не падая. Коммит `1c47ef8`.
2. **Корень** — `clearDependentFixtures()` в `packages/integrations/src/amo/oauth.test.ts:104`, вызывается и в `beforeEach`, и в `afterEach`. Тест сам чистит строки с внешними ключами на соединение, поэтому порядок прогонов перестал иметь значение: 574/574 проходят даже с оставленным в базе сидом. Коммит `289938f`.

Общее правило: **фикстура, которая удаляет строку, обязана сначала удалить всё, что на неё ссылается**. Правило «гонять E2E отдельно от юнитов» — организационный костыль, он не лечит хрупкость и однажды снова выдаст ложный диагноз.

Смежные грабли фикстур из этой же сессии:

- `cannot truncate a table referenced in a foreign key constraint` — новые таблицы снимков и публикаций ссылаются на прогоны и конфигурации; их надо дописывать **в начало** единого `truncate` во всех файлах сразу (`grep -rln "truncate table" --include="*.ts"`; в zsh кавычки у `--include` обязательны, иначе глоб съест шаблон).
- `Sales plan history is immutable` — строки `sales_plans` неизменяемы триггером, чистить только `truncate`, не `delete`.
- 7 из 9 тестов воркера падали с «sync run is not running»: триггер `app.require_running_sync_run()` (`supabase/migrations/0005_raw_sync.sql`) запрещает дописывать сырьё к завершённому прогону. Фикстура обязана вставить прогон со статусом `running`, добавить сырьё и только потом завершить его.

## 4. Ревизия против SPEC, а не против плана

«Все чек-боксы в планах закрыты» и «продукт соответствует спецификации» — разные утверждения. В этой сессии они разошлись: чек-боксы планов 3–5 проставлены коммитом `ec64905`, планов 1–2 — `7d60307`, а следующие три коммита (`b04fa96`, `289938f`, `9127774`) ещё дописывали экраны и чинили вёрстку.

Что вскрыла сверка `SPEC.md` ↔ фактические `apps/web/src/app/**/page.tsx` и `apps/web/src/app/api/**/route.ts` (grep по разделам SPEC и таблицам эндпоинтов):

- Обзор висел на `/dashboard`, а по SPEC M8.4 он должен быть на корне `/` (на корне была заглушка). Перенесли в `apps/web/src/app/page.tsx`, старый адрес оставили рабочим редиректом ради уже разосланных ссылок.
- Экранов `/leads/{amoLeadId}` и `/alerts` не существовало вовсе — только API.
- Действия существовали только в API: приёмка проблемы качества с обязательной причиной, постановка цели плана, регистрация/разметка/валидация/активация копии таблицы, отметка оповещения.
- Пропущены требования SPEC M8: доли оплат и выручки на каналах, всегда видимая группа «Неизвестный», доля этапа от входа и список застрявших дольше недели в воронке, группировка `/attention` по кодам причин.

Порядок приоритетов, подтверждённый практикой: **SPEC → METRICS_CATALOG → SECURITY_READ_ONLY → план**. Псевдокод плана иллюстративен. Конкретные случаи, где SPEC перевесил план:

- `missing_stage_history` **нельзя** принимать как исключение (SPEC M5.3), хотя псевдокод плана разрешал.
- Менеджер, запросивший чужой ключ, получает 403, а не тихую подмену фильтра на себя (SPEC M7.5).
- Отсутствие утверждённого снимка — 503 `E_CONFIG_INCOMPLETE`, а не 404.
- Формат параметров `manager=amo:42`, `compare=previous` берётся из SPEC, не из плана.

Имена файлов и номера миграций в планах тоже иллюстративны: миграция снимков получила `0011_metric_snapshots.sql` вместо «0006» из текста, публикация — `0012_sheet_publication_and_alerts.sql` вместо «0007», потому что порядок применения важнее иллюстративного имени, а 0005–0010 уже проверены и неизменяемы. Перед простановкой галочек по чужим планам 1–2 сначала проверялось фактическое наличие всех 131 названного файла.

Метод — часть более общего правила проекта: [[проект идет по Spec First и изменения сначала сверяются со спецификацией]].

## 5. Fail-closed публикация

Схема, по которой построена единственная внешняя запись проекта. Каждый шаг — отдельный барьер, и порядок барьеров существеннее их наличия. Развёрнутые запреты — [[исходная Google таблица навсегда защищена от записи]] и [[внешние интеграции должны иметь двойной switch и fail closed поведение]].

**Порядок проверок в `packages/integrations/src/google/policy.ts`, `createSheetWriteClient`:**

1. `assertWritableSpreadsheetId(...)` — формат по `/^[A-Za-z0-9_-]{20,200}$/`, защищённый идентификатор → `E_SHEET_PROTECTED` 403, чужая цель → `E_FORBIDDEN` 403.
2. `publishEnabledInEnvironment` — переменная окружения.
3. `controls.isPublishEnabled()` — флаг в БД.
4. И только теперь `secrets.readGoogleServiceAccount()` и создание клиента.

Смысл порядка: защищённая таблица не может породить запрос даже в принципе — проверка идёт **до** чтения секретов и до создания клиента (это подтверждено тестом «ноль запросов, ноль чтений ключа»). Выключенный деплой не ходит в базу за вторым контролем, потому что env-флаг проверяется раньше.

**Дублирование защиты:** идентификатор оригинальной таблицы заморожен константой в коде (`PROTECTED_SPREADSHEET_IDS` — `Object.freeze(new Set([...]))`, плюс `PROTECTED_SPREADSHEET_ID` в `packages/db/src/sheets.ts`) **и** запрещён check-констрейнтом в `supabase/migrations/0012_sheet_publication_and_alerts.sql`. Ни переменная окружения, ни строка в БД, ни запрос, ни интерфейс не могут сделать оригинал целью.

**Отпечаток раскладки** (`packages/integrations/src/google/layout.ts`, `computeLayoutFingerprint`) считается по именам листов и размерам сетки, **отсортированным по имени**. Поэтому публикация блокируется при реальном изменении структуры, но не при перетаскивании вкладки. Маппинг активной цели править нельзя — сначала возврат в статус `validated`.

**Сама публикация** (`packages/integrations/src/google/publisher.ts`, `publishPayload`):

- перед записью структура копии перечитывается и сверяется с отпечатком, зафиксированным при активации;
- все размеченные диапазоны уходят **одной пакетной записью**;
- результат читается обратно и сравнивается с отправленным через `readBackMatches` (`publisher.ts:65`), сверяется контрольная сумма нагрузки;
- расхождение → копия остаётся как была, пишется попытка `blocked`/`failed` с безопасным кодом, поднимается критический алерт и автопубликация выключается;
- `withPublicationRetries` повторяет **только** 429 и 5xx (`DEFAULT_RETRY_DELAYS` = 1, 3, 9, 27, 60 с, SPEC M9.5); несовпадение раскладки или контрольной суммы поднимается сразу, без ретраев.

**Асимметрия переключателей.** В `packages/db/src/identity.ts` есть `disableSystemControl` — она умеет только выключить флаг и записать причину (пустая причина → `E_CONFIGURATION`, текст обрезается до 500 символов). Парной функции включения нет намеренно: код имеет право погасить публикацию при расхождении, но включение внешней записи остаётся ручным решением человека (SECURITY_READ_ONLY §9).

Клиент Google написан вручную на `fetch` + `node:crypto` без SDK — три запроса (метаданные, чтение значений, одна пакетная запись) видны в одном файле и тестируются против локального фейкового сервера на `node:http`.

Тот же принцип «ничего наружу без двух согласий и без доказательства» действует и на входе — см. [[сырые amoCRM страницы append only и курсор двигается только после полного success]] и [[интеграция amoCRM только внешняя OAuth и только read-only]].

## 6. Точные деньги целыми копейками

Деньги никогда не проходят через `float` — ни в агрегации, ни в API, ни в CSV.

- Хранение и передача: брендированный строковый тип `Rubles` (`packages/domain/src/money/rubles.ts`) — строка с ровно двумя знаками, влезающая в `numeric(14,2)`. `MAX_AMO_PRICE_RUBLES = 999_999_999_999`.
- Арифметика: целые копейки в `BigInt`. `toKopecks` в `packages/domain/src/metrics/aggregate.ts:16` — `BigInt(целое) * 100n + BigInt(копейки)`, обратно через `formatKopecks`.
- Средний чек — `moneyAverage` с округлением half-up до копейки; при нулевом количестве оплат `null`, а не 0.
- Конверсии и `delta_pct` считаются от неокруглённых целых агрегатов, округление до одного знака — только для отображения; при нулевом знаменателе `null`, в интерфейсе длинное тире.
- Денежные итоги суммируются **до** округления.
- `parseAmoRubles`: amoCRM отдаёт `price` целым числом рублей. Всё, что не укладывается в правило, **рапортуется как проблема качества**, а не приводится: некорректная цена отклоняется даже у сделки, которая не является оплатой, а выигранный лид без валидной цены попадает в `won_without_valid_price` и считается оплатой, но не даёт выручки.
- Отображение (`apps/web/src/lib/dashboard/format.ts`): `Intl` `ru-RU`/`RUB` только для показа, строка остаётся источником правды. Грабля тестов: `Intl.NumberFormat` разделяет группы неразрывным пробелом U+00A0 — в ожиданиях нужна константа `NBSP`, обычный пробел не совпадёт.

Контрактный тест `tests/contracts/metrics.contract.test.ts` падает при расхождении в одну сделку или одну копейку — это и есть страховка от тихого дрейфа формул.

## Короткий чек-лист перед «готово»

1. Тесты красные → зелёные → мутации пойманы → исходники возвращены.
2. Экраны сняты скриншотами и просмотрены, а не только протестированы.
3. Наборы прогнаны в произвольном порядке (в том числе юниты после E2E).
4. Реализация сверена со `SPEC.md`, а не с чек-боксами плана.
5. Оба внешних переключателя остались выключенными, `pnpm check:secrets` и `git diff --check` чисты.
