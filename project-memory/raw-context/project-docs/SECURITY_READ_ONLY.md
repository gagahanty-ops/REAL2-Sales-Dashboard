# SECURITY_READ_ONLY.md — контракт безопасной интеграции

> Цель документа — сделать обещание «ничего не менять в amoCRM и исходной таблице» технически проверяемым, а не организационным пожеланием.

## 1. Защищаемые системы

1. Рабочий аккаунт amoCRM `555151.amocrm.ru`.
2. Исходная Google-таблица с ID `123QVhKGG3Y6ZlyHYnuKG_1BPhS82FcYaqY96nsB7Iks`.
3. OAuth client secret, access token и refresh token.
4. Персональные данные клиентов: имена, телефоны, тексты и идентификаторы сделок.
5. История продаж и рассчитанные показатели.

## 2. Модель доверия

- amoCRM является внешней системой истины и доступна приложению только для чтения бизнес-данных.
- PostgreSQL является внутренним аудиторским зеркалом, но не источником команд в amoCRM.
- Google Sheets является выходным представлением; только одна явно разрешённая копия может изменяться.
- Браузер пользователя не получает OAuth-токены amoCRM, service-role ключ БД или ключ service account Google.
- Любой компонент считается недоверенным, пока его действие не разрешено явным allowlist.

## 3. HTTP-политика amoCRM

### Разрешено

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/oauth2/access_token` | первичный обмен authorization code и обновление токена |
| `GET` | `/api/v4/account` | проверка аккаунта и часового пояса |
| `GET` | `/api/v4/leads/pipelines` и дочерние read paths | получение воронок и этапов |
| `GET` | `/api/v4/users` | справочник ответственных |
| `GET` | `/api/v4/leads` и `GET /api/v4/leads/{id}` | снимки сделок |
| `GET` | `/api/v4/leads/custom_fields` | чтение справочника полей для выбора источника |
| `GET` | `/api/v4/events` | история изменений и курсор синхронизации |

### Запрещено

- любой `POST` вне точного OAuth endpoint;
- любой `PATCH`, `PUT` или `DELETE` к amoCRM;
- generic proxy, принимающий произвольный method/path;
- массовое изменение сделок, задач, тегов, полей или статусов;
- создание webhook-подписок на MVP;
- браузерные запросы прямо в amoCRM с токеном;
- логирование тела OAuth-ответа.

### Принудительное исполнение

В проекте существует единственная функция транспорта `amoFetch(request)`. Она:

1. разбирает URL;
2. разрешает только подтверждённый amoCRM host аккаунта;
3. проверяет пару method/path по allowlist;
4. отклоняет запрос до сети с кодом `E_AMO_METHOD_DENIED` или `E_AMO_PATH_DENIED`;
5. записывает безопасный audit log: method, нормализованный path, status, duration, trace ID; query values и body не логируются.

Ни один модуль не импортирует глобальный `fetch` для запросов к amoCRM напрямую. Это проверяется статическим тестом.

## 4. OAuth и поддержка amoCRM

- Используется внешняя OAuth-интеграция amoCRM.
- Приватная интеграция и заявление об отказе от технической поддержки не используются.
- До production владелец аккаунта получает письменное подтверждение поддержки amoCRM, что установка внешней OAuth-интеграции не отменяет поддержку аккаунта.
- Redirect URI использует HTTPS и точное совпадение с зарегистрированным URI.
- OAuth `state` одноразовый, случайный и действует 10 минут.
- Refresh token вращается транзакционно: новый токен сохраняется до признания старого недействительным.
- Токены шифруются application key; в БД не хранятся открытым текстом.
- При повторной установке сверяется account ID; подключение другого аккаунта блокируется до явной административной процедуры.

## 5. Защита Google Sheets

### Жёсткий denylist

Константа `PROTECTED_SPREADSHEET_IDS` содержит:

```text
123QVhKGG3Y6ZlyHYnuKG_1BPhS82FcYaqY96nsB7Iks
```

Любая функция записи сначала проверяет target ID. Совпадение возвращает `E_SHEET_PROTECTED` до вызова Google API. Переменная окружения не может переопределить denylist.

### Allowlist таблицы-копии

- Production writer принимает ровно один `GOOGLE_TARGET_SPREADSHEET_ID`.
- Service account получает роль Editor только на таблицу-копию.
- Исходная таблица не расшаривается service account.
- Перед каждой публикацией проверяются target ID, заголовок, набор листов и layout fingerprint.
- Запись выполняется в staging-лист или временный диапазон; текущий отчёт заменяется только после полной проверки размера и контрольных итогов.
- При ошибке остаётся предыдущая опубликованная версия.

## 6. Доступ к дашборду и RLS

Роли:

- `admin` — OAuth, маппинг, планы, качество данных, все показатели;
- `head` — все показатели, drill-down и журнал синхронизаций без управления секретами;
- `manager` — только собственные агрегаты и сделки;
- `service_worker` — синхронизация и расчёт без пользовательского входа;
- `sheet_publisher` — чтение утверждённого снимка и запись только в разрешённую таблицу-копию.

Политика по умолчанию для всех таблиц — deny. `anon` не имеет доступа. Service credentials существуют только на сервере. Роль пользователя определяется из серверной сессии, а не из параметра запроса.

## 7. Персональные данные и логи

Обычные application logs не содержат:

- access/refresh tokens и authorization code;
- OAuth client secret;
- полные телефоны;
- полные имена клиентов;
- содержимое custom fields;
- полный raw payload amoCRM;
- Google service account private key.

Телефон в интерфейсе списка маскируется как `+7 *** ***-**-12`. Полный телефон доступен только через переход в amoCRM пользователю, который уже имеет права в amoCRM.

Raw payload хранится в БД с ограниченным доступом `service_worker` и `admin`, срок хранения — 90 дней. Нормализованная история и агрегаты хранятся без ограничения, пока действует проект.

## 8. Секреты

- `.env` и выгрузки токенов запрещены в Git.
- Production secrets находятся в secret store сервера.
- Локальная разработка использует отдельные тестовые значения и синтетические fixtures.
- Секрет, отправленный в чат или попавший в журнал, считается скомпрометированным и ротируется.
- Один секрет не используется одновременно в development и production.

## 9. Защита от частичных и ошибочных данных

- Каждый sync run имеет статусы `running`, `success`, `partial`, `failed`.
- Только `success` может породить новый production snapshot.
- `partial` и `failed` сохраняют диагностику, но не заменяют текущие цифры.
- Входные страницы API читаются в рамках одного логического запуска и получают общий `sync_run_id`.
- Ночная reconciliation сверяет количество и обновлённые ID по независимому полному проходу.
- Любое уменьшение числа сделок выше настроенного порога 5% блокирует публикацию и создаёт критический alert.

## 10. Обязательные проверки перед production

1. Unit test отклоняет POST/PATCH/PUT/DELETE на все business endpoints amoCRM.
2. Static test находит прямой импорт HTTP-клиента вне `amoFetch` и падает.
3. Integration test с mock server доказывает, что запрещённый запрос не дошёл до сети.
4. Test Google writer отклоняет защищённый spreadsheet ID при любых credentials.
5. Service account не видит исходную таблицу при проверке permissions.
6. Повторная синхронизация не создаёт новых lead/event rows.
7. Partial sync не меняет production snapshot.
8. Логи проходят secret/PII scanner.
9. Restore test поднимает БД из резервной копии.
10. Внешний health monitor подтверждает доступность dashboard и свежесть снимка.

## 11. Аварийное отключение

Один флаг `SYNC_ENABLED=false` останавливает новые обращения к amoCRM. Отдельный `SHEET_PUBLISH_ENABLED=false` немедленно выключает публикацию, не затрагивая чтение и дашборд.

При инциденте:

1. отключить публикацию;
2. отключить синхронизацию при подозрении на OAuth/amoCRM;
3. сохранить sync run ID и trace ID;
4. ротировать затронутый секрет;
5. сравнить последний корректный снимок и текущую БД;
6. восстанавливать публикацию только после повторного golden/reconciliation теста.

## 12. Критерий выполнения контракта

Read-only контракт считается выполненным только при одновременном наличии:

- автоматических тестов запретов;
- runtime audit log исходящих запросов;
- denylist исходной Google-таблицы;
- теневого периода без расхождений;
- письменного подтверждения по поддержке amoCRM;
- инструкции аварийного отключения, проверенной на staging.
