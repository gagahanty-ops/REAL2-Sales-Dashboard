# PROJECT_IDEA.md — дашборд отдела продаж РЕАЛ ДВА

> Слой 1 по Spec-First Methodology. Документ фиксирует, что и зачем строится. Технические контракты раскрыты в `SPEC.md`.
>
> Дата: 2026-09-12. Статус: проектирование. Код и интеграции не создавались.

---

## 1. Проблема

Отдел продаж РЕАЛ ДВА ведёт сделки в amoCRM, но ежедневный управленческий отчёт по менеджерам, каналам, заявкам, оплатам и выполнению плана переносится в Google Sheets вручную.

На предоставленном снимке воронки одновременно находилось **598 открытых сделок**, а в статусе «Успешно реализовано» — **388 сделок на 7 038 599 ₽**. Даже при таком объёме ручная таблица создаёт четыре системных риска:

1. **Двойной ввод.** Одно и то же событие сначала фиксируется в amoCRM, затем человек повторно переносит его в таблицу.
2. **Расхождение дат.** Заявка и оплата происходят позже создания лида, но бизнес-отчёт должен относить результат к дате создания лида. Ручное обновление прошлых дат легко пропустить.
3. **Разные трактовки источников.** В amoCRM встречаются UIS/звонок, WhatsApp, Avito, Instagram, сайт/Tilda, Telegram, MAX и «Без значения». Без единого справочника один канал распадается на несколько названий.
4. **Нет доказуемости цифр.** В текущем процессе нельзя автоматически пройти от агрегата в таблице до списка конкретных сделок и истории их этапов.

Критичное организационное ограничение: автоматизация не должна менять сделки, задачи, поля, статусы или настройки amoCRM и не должна приводить к отказу amoCRM в технической поддержке аккаунта.

## 2. Решение

Создать отдельный внутренний веб-дашборд с безопасным контуром чтения:

1. Пользователь устанавливает внешнюю OAuth-интеграцию amoCRM.
2. Сервис по расписанию читает целевую воронку, пользователей, этапы и события.
3. Ответы API сохраняются в неизменяемом сыром журнале.
4. Нормализатор строит историю стадий, ответственных и каналов, не отбрасывая непонятные значения.
5. Движок метрик относит все показатели к дате создания лида и рассчитывает срезы по дням, менеджерам и каналам.
6. Дашборд показывает обзор, план/факт, каналы, менеджеров, воронку, проблемные данные и историю синхронизаций.
7. После теневой приёмки рассчитанные значения атомарно публикуются в отдельную копию Google-таблицы.

Результат: amoCRM остаётся рабочей системой отдела продаж, а дашборд становится проверяемым управленческим представлением без второго ручного ввода.

## 3. Почему сейчас

- Объём воронки уже измеряется сотнями активных и реализованных сделок.
- Ручной отчёт существует и даёт готовый эталон для параллельной сверки.
- Внешняя OAuth-интеграция позволяет отделить аналитику от приватных интеграций amoCRM.
- Существующие внутренние проекты уже доказали нужные паттерны: журнал синхронизаций, идемпотентность, staging, golden-тесты, роли и сохранение последнего корректного снимка.
- Чем дольше отчёт ведётся вручную, тем больше исторических корректировок нужно будет восстанавливать при переходе.

## 4. Целевая аудитория

### Основная

**Руководитель отдела продаж и собственник.** Им нужны показатели всего отдела: план/факт, заявки, оплаты, выручка, конверсии, менеджеры, каналы и сделки, требующие внимания.

### Вторичная

**Менеджер отдела продаж.** После включения ролевого доступа видит только собственные показатели и сделки, относящиеся к его ответственности.

### Техническая

**Администратор интеграции.** Контролирует OAuth-подключение, маппинг воронки, справочник каналов, свежесть данных и ошибки синхронизации. Администратор не получает интерфейса для изменения сделок amoCRM.

## 5. Архитектура

```text
amoCRM External OAuth
        ↓  GET account/pipelines/users/leads/events
Read-only API client
        ↓
Raw journal (append-only) → Sync runs and diagnostics
        ↓
Normalization → lead facts + stage history + attribution quality
        ↓
Metrics engine → daily/manager/channel/funnel aggregates
        ↓
Versioned dashboard snapshot
        ├── Web dashboard
        └── Google Sheets publisher → duplicate spreadsheet only
```

### Стек

- **Web:** Next.js 16, React 19, TypeScript — серверный рендеринг внутреннего дашборда, типизированные маршруты и единый проект для UI/API.
- **UI:** Tailwind CSS, shadcn/ui, Recharts — проверенный стек существующего Sales Analytics Dashboard.
- **Database/Auth:** Supabase Pro: PostgreSQL 17, Auth, RLS и ежедневные резервные копии; бесплатный тариф с автопаузой для production запрещён.
- **Sync worker:** отдельный Node.js-процесс на сервере, запускающий инкрементальную синхронизацию каждые 5 минут и полную сверку ночью.
- **amoCRM:** внешняя OAuth-интеграция; прикладной клиент допускает только GET.
- **Google Sheets:** Google Sheets API через отдельный service account, которому предоставлен доступ только к таблице-копии.
- **Deployment:** Docker-контейнеры `web` и `worker` на отдельном сервере; база — управляемая. Секреты находятся только в переменных окружения production.

## 6. Экономическая модель

Это внутренний инструмент, а не SaaS-продукт с тарифами.

Экономический результат измеряется тремя величинами:

1. доля строк ежедневного отчёта, заполненных автоматически — целевое значение **100% расчётных ячеек**;
2. расхождение с проверенным ручным эталоном — **0 сделок и 0 ₽** для целых исходных значений;
3. время от изменения сделки в amoCRM до появления в дашборде — **не более 10 минут для 95% синхронизаций**.

Операционные расходы включают сервер, управляемую БД, резервные копии и мониторинг. Разработка, amoCRM и Google Workspace считаются отдельными существующими расходами и не маскируются под стоимость эксплуатации дашборда.

## 7. Альтернативы и конкуренты

| Альтернатива | Что умеет | Почему не решает задачу полностью |
|---|---|---|
| Ручная Google-таблица | Даёт привычный ежедневный отчёт | Двойной ввод, человеческие ошибки, нет журнала и drill-down |
| Аналитика amoCRM | Показывает стандартные отчёты по CRM | Не воспроизводит точную форму текущей таблицы и бизнес-правило когорты по дате создания |
| Только Apps Script | Может читать API и писать в Sheet | Ограниченная наблюдаемость, квоты, сложнее тестировать историю событий и безопасный повторный запуск |
| n8n как единственное ядро | Быстро связывает API и Sheets | Расчёты и исторические пересчёты становятся трудно проверяемыми; workflow превращается в критическую монолитную точку отказа |
| Отдельный BI поверх выгрузки | Строит графики | Не решает надёжную синхронизацию, историю этапов и атомарную публикацию в существующую форму |

Отличие предлагаемого решения — проверяемый read-only контур с историей событий, контролем качества и отдельной совместимой выгрузкой в Google Sheets.

## 8. План запуска

### Фаза 0 — документация

Утвердить определения метрик, архитектурные ограничения, модули, данные, API, UI, ошибки и критерии приёмки. Результат — документы слоя 1 и 2 без программного кода.

### Фаза 1 — безопасный read-only контур

Подключить внешнюю OAuth-интеграцию, проверить account/pipeline/status IDs, получить пользователей и выполнить первичный backfill без публикации. Критерий: журнал доказывает отсутствие прикладных HTTP-методов кроме GET.

### Фаза 2 — расчётный MVP

Построить нормализацию, каталог метрик, обзор, менеджеров, каналы и drill-down. Критерий: golden-набор воспроизводится точно и повторный запуск ничего не дублирует.

### Фаза 3 — теневой режим

Запускать расчёты параллельно ручной таблице 7–14 календарных дней. Каждый день формировать reconciliation-отчёт. Публикация в Google Sheets выключена.

### Фаза 4 — публикация в копию

Создать или выбрать таблицу-копию, проверить denylist исходной таблицы и включить атомарную публикацию. Критерий: две последовательные публикации одного снимка дают одинаковый результат.

### Фаза 5 — production

Включить расписание, алерты, резервные копии и runbook восстановления. Исходная таблица и amoCRM остаются недоступными для записи.

### За пределами MVP

- изменение сделок, задач, тегов, статусов или полей amoCRM;
- автоматические сообщения клиентам;
- замена интерфейса amoCRM;
- рекламные расходы, CAC и ROMI без отдельного подтверждённого источника затрат;
- прогнозирование продаж и AI-рекомендации;
- мобильное приложение.

## 9. Риски

| Риск | Вероятность | Ущерб | Митигация |
|---|---|---|---|
| Ошибочный запрос изменит amoCRM | Низкая после мер | Критичный | GET-only клиент, deny-by-default transport, тест запрета методов, аудит исходящих запросов |
| Внешняя интеграция повлияет на поддержку amoCRM | Низкая | Критичный | Не использовать приватную интеграцию; до production получить письменное подтверждение поддержки amoCRM |
| Повторная синхронизация задублирует сделки | Средняя | Высокий | Уникальные ключи amo ID/event ID, upsert, курсоры и тест повторного запуска |
| Смена названия этапа сломает расчёт | Средняя | Высокий | Считать по ID, название использовать только для первичной проверки; fail closed при исчезновении ID |
| История API неполная | Средняя | Высокий | Первичный backfill + ежедневная полная сверка + качество атрибуции в каждой записи |
| Источник сделки неоднозначен | Высокая | Средний | Явный приоритет правил; значение `unknown`; очередь разбора; запрет угадывания |
| amoCRM временно недоступна или отвечает 429 | Средняя | Средний | Backoff с jitter; сохранить последний успешный снимок; не публиковать частичный расчёт |
| Таблица-копия изменена вручную | Средняя | Средний | Версионированная область вывода, проверка заголовков и контрольной сигнатуры перед публикацией |
| Сервисный аккаунт получил доступ к оригиналу | Низкая | Критичный | Жёсткий denylist spreadsheet ID независимо от Google permissions |
| Ошибка часового пояса сдвинет дату | Средняя | Высокий | Все бизнес-даты вычислять в `Europe/Moscow`; golden-тесты около полуночи и DST-независимые ISO-дни |
| База данных остановится из-за бесплатного тарифа | Средняя без меры | Высокий | Production только на тарифе без автопаузы, health check и резервные копии |

### Архитектурные инварианты

- dashboard никогда не является источником данных для amoCRM;
- частичная синхронизация не может заменить последний корректный снимок;
- сырые ответы и события append-only;
- неизвестное значение сохраняется вместе с причиной;
- каждая агрегированная цифра раскрывается до amo lead ID и исходного события;
- бизнес-формулы определены только в `METRICS_CATALOG.md`;
- исходная Google-таблица защищена denylist на всех путях публикации;
- реальные телефоны, токены и payload не попадают в обычные application logs.

### Production AI

Продакшн AI/LLM-агентов в продукте нет. AI используется только для разработки. Поэтому отдельный продуктовый `ai-agent-architect` этому проекту не требуется.
