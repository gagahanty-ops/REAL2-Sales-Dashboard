# Установка внешней OAuth-интеграции amoCRM

Этот runbook используется только владельцем аккаунта и ответственным
администратором после прохождения staging-gate. Он не разрешает подключать
приватную интеграцию и не разрешает изменять данные amoCRM.

## Обязательные условия до начала

- В amoCRM регистрируется именно **внешняя OAuth-интеграция**.
- Получено и сохранено письменное подтверждение поддержки amoCRM: установка
  внешней OAuth-интеграции не отменяет техническую поддержку аккаунта.
- Подтверждён аккаунт `555151.amocrm.ru`.
- `SYNC_ENABLED=false` и `SHEET_PUBLISH_ENABLED=false` в окружении.
- В БД `system_controls.sync_enabled=false` и
  `system_controls.sheet_publish_enabled=false`.
- Security-, integration-, contract-тесты и сборка прошли на том же коммите,
  который устанавливается на staging.

Если хотя бы один пункт не выполнен, установку не начинать.

## Регистрация интеграции

1. Создать внешнюю интеграцию в аккаунте amoCRM. Не выбирать приватную
   интеграцию и не подписывать отказ от поддержки.
2. Указать единственный Redirect URI:

   ```text
   https://<утвержденный-домен>/api/integrations/amo/callback
   ```

   Значение должно посимвольно совпадать с `AMO_REDIRECT_URI` в secret store.
   HTTP, дополнительный slash, другой host или query-параметры запрещены.
3. Выдать только доступ, необходимый для чтения аккаунта, пользователей,
   сделок, воронок, статусов, полей и событий. Права на изменение сущностей,
   Digital Pipeline, роботов, задачи и сообщения проекту не требуются.
4. Поместить `AMO_CLIENT_ID` и `AMO_CLIENT_SECRET` только в серверный secret
   store. Не отправлять их в чат, тикет, документ, Git или браузерный код.
5. Оставить оба environment switch и оба DB-control выключенными.

## Проверка подключения на staging

1. Администратор открывает `/settings/integrations/amo` и запускает OAuth.
2. После callback система обязана сверить через API:
   - host `555151.amocrm.ru`;
   - subdomain `555151`;
   - API account ID, возвращённый самим amoCRM.
3. Нажать «Проверить чтение». Успех означает только разрешённый
   `GET /api/v4/account`; синхронизация при этом не включается.
4. Сохранить без секретов: commit SHA, время по Москве, безопасный trace ID,
   результат проверки и ссылку на письменное подтверждение поддержки.
5. Проверить audit: business-запросы только `GET`; единственный допустимый
   `POST` — `/oauth2/access_token` для обмена/обновления токена.

## Критерий завершения

Подключение считается подготовленным только когда проверка аккаунта успешна,
секреты отсутствуют в логах и Git, письменное подтверждение поддержки
приложено к change record, а `SYNC_ENABLED` и DB-control по-прежнему `false`.
Включение синхронизации — отдельное решение владельца после shadow-gate.
